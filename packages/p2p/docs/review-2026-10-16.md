# P2P review and proposed improvements

Reviewed 16 October 2026 against `6dfc1aafc0dca91534e637b7e30dece6b5c94069`.
Three parallel reviews covered transport/trust, RPC and databases/replication.
This document is a proposal for review, not a claim that the new APIs exist.
The current package is unpublished alpha; Personal Node and collaborative
database scaffolds remain experimental/deferred.

### Implementation follow-up

The correctness work and initial API prototypes were subsequently implemented:
transactional identity/invites, single-runtime ownership, RPC single-execution
and kind checks, bounded handshake/cancellation/lifecycle cleanup, staged manifest
replacement, persisted discovery/mirroring pause and secured scaffold reducers.
The typed [RPC guide](rpc.md), experimental [database guide](db.md) and
[validation commands](../../../docs/validation.md) now describe the shipped source.
The findings below preserve the original review; their source line numbers refer
to the reviewed revision rather than the changed implementation.

Safe refreshes include Hyperswarm 4.17.2, Protomux 3.13.0, b4a 1.9.0,
bare-events 2.9.2 and explicit native filesystem/locking dependencies. Direct
compact-encoding remains on v2, Hyperdrive on v12 and the existing Autobee
scaffold on 1.0.10. Autobase 7.28.2 is an explicitly installed optional engine
for the separate prototype. Fresh Bare consumers require >=1.32.0; installed
acceptance uses the maintained desktop sidecar's 1.34.1.

Still deferred: stable peer handles across reconnect, suspend/resume convenience,
full channel pause, shared-resource ACL/retention, resumable subscriptions,
complete collaborative database backup/migration and the later service proposals.

## Recommendation

Keep one P2P package, divide its implementation into clear parts, and offer a
small friendly API over them. Fix the confirmed correctness problems before
expanding its public surface. Add a lightweight typed RPC layer and prototype
database integration around upstream engines; do not build a new database engine.

| Part | What developers should get | Public location |
| --- | --- | --- |
| Connections and identity | Start/stop, pair, reconnect, suspend/resume and observable peer state | Package root; internal modules |
| Trust | Scoped invitations, approval, permissions and revocation | Package root; internal modules |
| RPC | Ordinary async functions, typed inputs/results and explicit streams | Existing root API, optional procedure helpers to design |
| Replication | Retain data/files, report honest protection state and enforce policy | Existing `/sync` |
| Databases | Local lifecycle, writer membership, database-aware replication and recovery | Proposed optional `/db` |
| File transfer | Scoped binary retrieval, ranges, limits and cancellation | Proposed later `/files` |
| Live events | Bounded subscriptions with optional cursor-based recovery | Shared RPC primitive; separate entry point only if useful |

This is a division of responsibilities, not seven npm packages. Keep low-level
transport and permission machinery behind a stable façade. Applications own
schemas, business rules and UI; Personal Node owns host policy and native compute.

## Fix these before adding features

Priority P1 means fix before broader alpha adoption or extracting the affected
implementation into a reusable API. P2 means important robustness/design work.
“Reproduced” refers to targeted local probes, separate from the existing suite.

| Priority | Problem and user impact | Evidence | Proposed change |
| --- | --- | --- | --- |
| P1 | Awaiting one `peer.api` handle twice can run a mutation twice | Reproduced: two awaits produced two invocations; [lazy handle](../src/peer.js#L84) | Cache the unary promise immediately; then replace the dual-mode handle with normal Promise/AsyncIterable return types |
| P1 | Calling a unary method as a stream can hang after its result arrives | Reproduced; [response dispatch](../src/peer.js#L281) ignores RESULT for stream queues | Advertise/check method kind and reject response mismatches; add caller stream deadlines |
| P1 | Concurrent first use of one storage directory can create different identities | Reproduced: eight concurrent initializers returned eight keys; [identity creation](../src/identity.js#L12) | Exclusive cross-process seed creation with loser reread; one live networking owner per identity |
| P1 | A stale CLI invite write can bring a spent invitation back to life | Reproduced with two stores; [invite persistence](../src/invite-store.js#L16) | One transactional mutation owner, or locking plus reload inside every transaction; atomic rename alone is insufficient |
| P1 | Failed manifest replacement leaves resources partially attached | Reproduced with real Corestore; [manifest application](../src/sync/index.js#L32) changes live state before persistence | Preflight, stage, commit durable intent and recover/rollback; serialize changes per owner |
| P1 | Generated collaborative membership operations do not verify an administrator | Source review; [generated apply](../../cli/src/generators/common.ts#L161) promotes the supplied key | Authenticate the source writer; deterministic membership roles and operation validation; disable optimistic input by default pending explicit policy |
| P2 | Discovery/pairing operations overwrite each other's pending state | Source review; [discover](../src/node.js#L182), [pair](../src/node.js#L321) | Correlate operations by expected peer/topic/invite; coalesce identical operations or reject unsupported concurrency |
| P2 | Close can race with opening or failed pack attachment | Source review; [opening](../src/node.js#L93), [closing](../src/node.js#L857) | Explicit lifecycle state, shared close promise, startup rollback and cancellation |
| P2 | Unpaired sockets can retain all available peer slots | Source review; [connection admission](../src/node.js#L370) has no handshake deadline | Separate pending/paired limits and HELLO/pairing/approval deadlines |
| P2 | Pause is weaker than its name suggests and resets after restart | Restart reset reproduced; [pause](../src/sync/replication.js#L193), [socket replication](../src/sync/index.js#L160) | Persist pause intent; separately define discovery, downloading and full replication pause |
| P2 | Wall-clock conflict policy can suppress valid writes from other devices | Source review; [generated merge](../../cli/src/generators/common.ts#L170) | Deterministic operation order as a simple default; explicit causal/conflict policy for apps needing stronger semantics |
| P2 | Shared database resources can belong to only one device | [Ownership check](../src/sync/replication.js#L40) rejects a second owner | Resource-level ACL/reference counting; separate each device's registration and retention intent |

Membership risk deserves precision: pinned Autobee 1.0.10 permits optimistic
input by default, while the generated apply function accepts membership commands
without checking their origin. Any accepted writer can currently promote another.
Unknown-writer self-promotion is a credible source-supported path, but was not
demonstrated end to end in this review. Test that path before stating exploitability.

Timeouts also need honest semantics. A handler that ignores its AbortSignal can
retain an execution slot after timeout/disconnect. This was reproduced. Simply
freeing the slot would permit unlimited underlying work; separate logical request
cleanup from execution accounting, and isolate expensive/untrusted handlers in
workers when forced termination is required.

## Connections should feel simple

Keep the current `createNode`, `listen`, `pair` and `connect` vocabulary initially.
Prefer additive conveniences over renaming every method at once:

```ts
// Proposed additions, not current callable APIs.
const node = createNode({ storage: './.my-app', capabilities: [notes] })
await node.listen({ signal })
const peer = await node.pair(code, { signal, reconnect: true })

const stopObserving = peer.observe(state => renderConnection(state))
await peer.waitUntilConnected({ signal, timeout: 10_000 })
// The peer handle remains useful across transport reconnects.

await node.suspend() // OS sleep/background integration
await node.resume()
stopObserving()
await node.close()
```

Add AbortSignal support to discovery/dial/pair operations, validated retry
options, jittered backoff and an explicit way to stop reconnecting. A stable
peer handle should bind to replaceable sessions; it must not silently replay
in-flight requests after reconnect.

Release discovery/dial intent on completion, timeout and cancellation using
reference-counted leases. A topic used by another capability must remain joined.
Show authenticated fingerprints separately from self-reported device/app names.
The default “machine-local” topic is a guessable DHT rendezvous derived from
user/hostname; it does not prove locality or implement LAN-only discovery.

## RPC: borrow the useful parts of tRPC

The target experience is an ordinary function call with autocomplete and useful
errors. We do not need tRPC's HTTP stack, React integrations, batching or a large
framework to get there. Keep existing dynamic calls available for JavaScript and
independently developed peers.

```ts
// Proposed design sketch. Helpers and names need a prototype.
const notes = defineCapability({
  name: 'notes',
  version: 1,
  methods: {
    get: procedure.input(noteIdSchema).output(noteSchema)
      .query(async ({ input, signal }) => db.get(input.id, { signal })),
    create: procedure.input(newNoteSchema).output(noteSchema)
      .mutation(async ({ input, peer, signal }) => createNote(input, peer, signal)),
    changes: procedure.input(cursorSchema).output(changeSchema)
      .stream(async function* ({ input, signal }) {
        yield* changeLog.read({ after: input.after, signal })
      })
  }
})

// Type-only contracts provide autocomplete; runtime contracts validate peers.
const api = peer.client<typeof notes>({ name: 'notes', version: 1 })
const note = await api.get({ id: 'n1' }, { signal })
for await (const change of api.changes({ after: cursor }, { signal })) {
  renderChange(change)
}
```

The first milestone should provide:

- Explicit unary/stream kinds, with ordinary Promise/AsyncIterable returns.
- Input, output and per-chunk runtime validation, plus inferred TypeScript types.
  A small parser/Standard Schema adapter avoids forcing every app to use Zod.
- A package `types` export and compile-time wrong-input/wrong-output tests.
- Runtime checks for service name/version/kind and peer grants. Type parameters
  alone cannot prove a remote implementation matches; shared runtime contracts
  should validate received output as well. Keep contracts separate from server code.
- Structured, bounded public errors; local diagnostics retain internal causes.
  Normalize strings/null thrown by handlers and enforce one terminal response.
- Explicit JSON value rules and deadline/cancellation semantics. Large binary data
  belongs on an appropriate mux channel, not encoded as control JSON.

Marking query/mutation informs policy, not permission. Neither is automatically
safe to retry. A disconnect after execution but before acknowledgement means the
outcome is unknown. Mutation retries require a service-owned operation ID and
durable deduplication policy; no generic exactly-once promise.

Current streams have a 120-second host deadline and 1 MiB lifetime budget. Those
are sensible bounded-work defaults, but ordinary long-lived subscriptions need a
separate policy: idle deadlines, rolling byte/rate budgets, overflow behavior,
cursors, retention and gap detection. Existing transport drain is not the same
as end-to-end consumer credit.

The design borrows procedure contracts and tracked subscription concepts from
[tRPC procedures](https://trpc.io/docs/server/procedures),
[validators](https://trpc.io/docs/server/validators) and
[subscriptions](https://trpc.io/docs/server/subscriptions). It does not propose
installing tRPC as the P2P transport.

## Databases: integrate engines, make distributed semantics explicit

**Autobase is relevant and should be evaluated directly.** It provides ordering
and replay for multiwriter views. It does not decide the application's conflict,
permission, uniqueness or recovery policy. Its apply function must be deterministic;
views can be undone/reapplied as ordering evolves. External side effects such as
notifications, payments and jobs must not run inside apply.

An important correction: this repository's pinned Autobee 1.0.10 is already a
separate implementation, with no Autobase dependency. Its name/API resemblance
does not make it an interchangeable wrapper. Latest Autobee is also experimental.
Compare adapters deliberately; do not replace the dependency under an existing
database and assume its data format, membership or recovery remains compatible.

Start with explicit engine choices: single-writer Hyperbee, a narrowly scoped
Autobase collaborative prototype, and migration evaluation for existing Autobee
scaffolds. HyperDB supplies application schema/index integration where appropriate.
Avoid promising one generic ORM across all of them.

```ts
// Proposed integration, not an existing API.
import { openDatabase, autobaseAdapter } from '@unstoppable-stack/p2p/db'

const db = await openDatabase({
  node,
  store,
  adapter: autobaseAdapter({ openView, apply }),
  key: databaseKey,
  encryptionKey
})

await db.append({ type: 'note.edit', operationId, id, patch })
const note = await db.view.get(id)
await db.sync.wait({ checkpoint, timeout: 10_000, signal })
await db.members.add(writerKey, { role: 'writer', indexer: false })
await db.close()
```

The exact façade should follow a working two-device prototype. Required behavior:

| Concern | Contract to define |
| --- | --- |
| Offline use | Local readiness, reads and eligible writes work without a reachable peer; network waits are explicit |
| Save confidence | Distinguish appended locally, applied locally, replicated to host and confirmed checkpoint |
| Conflicts | Define update/update, delete/update, duplicates and uniqueness; expose conflicts when silent loss is unacceptable |
| Membership | Authenticate operation source; separate reader, writer, administrator and indexer; define offline revocation ordering |
| Liveness | Document which unavailable indexers prevent stable progress; do not promote every writer to indexer automatically |
| Replay/migrations | Bounded versioned operations, deterministic invalid-op handling, rebuildable views and compatible schema evolution |
| Encryption | Separate transport authentication, read-key possession and writer authority; removing a writer does not erase copies or rotate read keys |
| Replication | Adapter owns all required writer/system/view feeds and wakeup integration, not just the latest materialized view |
| Recovery | Retain database graph, keys and checkpoint evidence; test reconstruction with original devices powered off |
| Lifecycle | Close snapshots, watchers and replication sessions; handle sparse/missing data, cancellation and shutdown |

The existing `multi-writer` + `node-sync` restriction is valid and should remain
until database-aware replication/recovery exists. A derived Hyperbee view alone
does not establish a complete collaborative database backup.

The Node CLI currently attaches `store.replicate(conn)` while the desktop
generator uses `db.autobee.replicate(conn)` for additional wakeup behavior.
Extract the adapter-owned attachment so both targets use the same semantics.

Control-plane grants do not automatically authorize every binary replication
channel. Current sync attaches the root Corestore to all swarm sockets, including
resource-discovery peers. Define whether a resource is intentionally seedable by
key possession or must require an authorized replication session. Treat read-key
distribution and rotation as a separate confidentiality boundary; a method grant
alone must not be described as encrypting stored data or revoking downloaded bytes.

The review also corrected stale backup documentation: current Personal Node v2
settings export includes the identity seed and revocation records in plaintext,
as well as settings and peer metadata. It does not include replicated payloads.
Identity import/clone must not leave two live hosts competing under the same key.

## Common app capabilities worth adding

| Capability | Why it helps | Recommendation |
| --- | --- | --- |
| Connection/service state | Every app needs offline, reconnecting, denied and unavailable states | Add early through local observation and stable peer handles |
| Resumable changes | Chat, task lists and notifications need live updates without missing gaps | Add after typed RPC; cursor/retention contract, not automatic replay of arbitrary streams |
| Files and attachments | Photos/documents need bounded binary reads, ranges, progress and cancellation | Next optional integration after sync policy fixes |
| Database observation | Reactive local views need snapshots/change events and clear convergence status | Include in the `/db` prototype |
| Presence | Useful online/away/typing state | Later small pack; ephemeral, expiry-based and separate from durable database truth |
| Request deduplication | Prevent duplicate user actions when callers retry an uncertain result | Small opt-in helper plus service-owned durable store; define retention and operation scope |
| Background jobs | Long operations need progress, cancellation, durable status and recovery | Later separate host service; RPC alone is not a durable queue or execution sandbox |

Keep accounts, domain search, payments, model providers and arbitrary remote code
execution outside the P2P core. They may use capability handlers with their own
permissions and lifecycle. A local log event is not a durable notification inbox.

## Delivery order and acceptance

1. **Correctness:** identity/invite transactions; one-shot RPC handles; method-kind
   checks; startup/teardown coordination; operation correlation and handshake limits;
   manifest failure recovery and precise persisted pause policy. Add regression tests.
2. **Friendly RPC:** typed procedures, runtime validation, service compatibility,
   stable peer handles, bounded errors, cancellation and connection-state observation.
3. **Database prototype:** two devices edit offline, reconnect and converge through
   an explicit adapter. Test membership attacks, reader promotion, clock skew,
   delete/update races, malformed operations and unavailable indexers.
4. **Recovery and events:** fresh-device reconstruction from Personal Node without
   original devices; shared-resource ownership; encryption/revocation and bounded
   resumable change streams. Then add scoped file retrieval as a real consumer.
5. **Dependency migrations:** land separately with old/new interoperability and
   installed-artifact Node/Bare tests, not mixed into the API redesign.

The existing P2P suite passed **99 tests** during this review. Targeted probes
still found uncovered failures. Protocol/mock/local-DHT success does not establish
public-network reachability, native inference or packaged desktop acceptance.
Follow the [validation guide](../../../docs/validation.md) for those boundaries.
