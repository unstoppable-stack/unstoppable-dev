Autobase

Multi-writer consensus for Hypercore

How QVAC's registry turns multiple independent writers
into a single consistent database — over P2P.

Holepunch Event Sourcing P2P Multi-Writer

The Problem: Single-Writer Hypercore

A Hypercore is an append-only log that only one key holder can write to.

┌──────────────────────────────────────────┐ │ Hypercore │ │ │ │ [block0] [block1] [block2] [block3] ... │ │ │ │ Only the key-holder can append. │ │ Anyone with the public key can read. │ └──────────────────────────────────────────┘

Single point of failure

  • Server goes down → nobody can write
  • Lose the key → lose write access forever
  • Can't safely backup a live corestore

What we need

  • Multiple servers that can all write
  • A consistent view despite concurrent writes
  • Resilience — 1 writer down, service stays up

Autobase in One Sentence

Autobase takes multiple independent Hypercore writers,
linearizes their operations into one consistent order,
and produces a deterministic view (your database).

Think of it as event sourcing over P2P — each writer is an event log, Autobase is the reducer.

Core Concepts

Writers

Each participant has a local Hypercore (their "writer core"). They append operations to it independently.

Linearizer

Takes the causal DAG of all writers and produces a single, deterministic ordering of operations.

Indexers

Writers promoted to build the view. A majority quorum of indexers must be online for the signed length to advance.

Operations

Encoded commands appended by writers: put-model, add-indexer, delete-model, etc.

View

The output — a derived data structure (in QVAC: a HyperDB database) created by applying operations in order.

Signed Length

A checkpoint where ordering is permanently locked. Advances as indexers acknowledge state.

How It Works: The Causal DAG

Each operation references the previous ones it "knows about", forming a directed acyclic graph:

Writer A: [op1] ──→ [op3] ──────────→ [op6] ↑ ↑ Writer B: [op2] ─┘──→ [op4] ──→ [op5]─┘ ───────────────────────────────────────────────── Linearized order: op1, op2, op3, op4, op5, op6 ───────────────────────────────────────────────── Rules: • An operation never precedes one it references • Independent operations may be reordered as new info arrives • Once signed (checkpointed), order is permanent

The linearizer analyzes causal references to produce an order that is eventually consistent across all peers.

Event Sourcing Pattern

Autobase separates what happened (operations) from current state (view):

┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ Writer 1 │ │ Writer 2 │ │ Writer 3 │ │ (local │ │ (local │ │ (local │ │ core) │ │ core) │ │ core) │ └──────┬──────┘ └──────┬──────┘ └──────┬──────┘ │ │ │ └────────┬────────┴──────────────────┘ │ ▼ ┌────────────────┐ │ Linearizer │ Orders operations │ (Causal DAG) │ using causal refs └───────┬────────┘ │ ▼ ┌────────────────┐ │ apply(nodes, │ Your custom function │ view, base) │ applies each op to view └───────┬────────┘ │ ▼ ┌────────────────┐ │ View │ The database / state │ (HyperDB) │ that clients query └────────────────┘

You Provide Two Functions

open(store)

Creates the view data structure. Called once.

function open(store) {
  const dbCore = store.get('db-view')
  return new RegistryDatabase(dbCore, {
    extension: false
  })
}

The store is an isolated Autobase-managed Corestore. extension: false is required for Autobase compatibility.

apply(nodes, view, base)

Applies linearized operations to the view. Called as operations arrive.

async function apply(nodes, view, base) {
  for (const node of nodes) {
    // node.value = encoded operation
    // Decode and route to handler
    await router.dispatch(node.value, {
      view,
      base
    })
  }
}

Must be deterministic — same inputs must always produce same outputs. Only modify the view, never external state.

Reordering: Why Determinism Matters

When a causal fork is discovered, Autobase may need to reorder operations:

Time 1: Writer A says [op1, op2, op3] Time 2: Writer B connects — has [opX] between op1 and op2 Before: op1 → op2 → op3 After: op1 → opX → op2 → op3 ↑ inserted here! Autobase automatically: 1. Undoes op3, op2 from the view 2. Applies opX, op2, op3 in new order 3. View is rebuilt correctly

This only works if apply is purely deterministic — it must produce the exact same view given the same operations in the same order.

Once operations pass the signed length checkpoint, they're permanent and won't be reordered.

Writers vs. Indexers

Writer Indexer
Can append operations? Yes Yes (indexers are writers too)
Builds the view? No Yes
Advances signed length? No Yes (majority quorum required)
Acknowledges state? No Yes (via ack / ackInterval)
Typical role Submitter / contributor Server node / consensus participant

In the QVAC registry, all server instances are indexers. Clients are read-only — they just replicate the view.

Quorum = majority of indexers. With 3 indexers, you need 2 online to advance the signed length.

Acknowledgements (Acks)

Indexers periodically "ack" — append a null value that references the latest state they've seen.

Indexer A: [op1] ───→ [ack] ───→ [op4] ───→ [ack] ↑ ↑ Indexer B: [op2] ──→ [op3] ───→ [ack] ────────┘ ↑ Indexer C: [ack] ─┘ When a majority of indexers ack a point → signed length advances Everything before signed length is PERMANENT (no more reordering)

ackInterval

Auto-ack timer in milliseconds. In QVAC registry: 5000ms. Forces convergence even when no real writes happen.

ackThreshold

Minimum number of unacked operations before an ack is triggered. 0 means ack freely.

How QVAC Registry Uses Autobase

The registry server creates an Autobase with the Hyperdispatch router pattern:

this.base = new Autobase(this.store, this.autobaseBootstrap, {
  open:  this._openAutobase.bind(this),   // Creates a RegistryDatabase view
  apply: this._apply.bind(this),          // Routes operations via Hyperdispatch
  close: this._closeAutobase.bind(this),
  ackInterval: 5000,
  ackThreshold: 0
})

Defined Operations

  • put-model — add or update a model entry
  • put-license — add a license record
  • delete-model — remove a model
  • add-indexer — promote a writer to indexer
  • remove-indexer — demote an indexer

All operations are encoded via Hyperdispatch schemas, decoded in the apply handler, and routed to the correct handler function.

Write Flow: Adding a Model

  1. Admin calls addModel() via RPC (or directly on the server)
  2. Server downloads the file from HuggingFace or S3 to a temp directory
  3. File is uploaded to Hyperblobs (binary storage), returning a blob pointer
  4. Server encodes a put-model operation with metadata + blob pointer
  5. Operation is appended to the local writer core: base.append(encodedOp)
  6. Autobase linearizer picks it up, calls apply()
  7. Apply handler routes to view.putModel(model) — written to HyperDB
  8. Blob core is mirrored to blind peers for 24/7 availability

From the client's perspective: they replicate the view (HyperDB) and see the new model appear.

Read Flow: Clients

Clients never write to the Autobase. They only replicate the view core.

┌──────────┐ ┌──────────┐ │ Server │ │ Client │ │ (writer/ │ Hyperswarm replication │ (read- │ │ indexer) │ ◄────────────────────────► │ only) │ └────┬─────┘ └────┬─────┘ │ │ ▼ ▼ Autobase view core ──────────────────► Replicated copy (RegistryDatabase) (RegistryDatabase) │ │ Swarm topics joined: │ • base.discoveryKey (autobase system) │ • view.discoveryKey (the database) │ • rpcDiscoveryKey (admin RPC - server only) │ │ Client only needs: │ • view.discoveryKey (to sync the database) │ • blob core keys (to download files)

The view is a regular Hypercore — clients join its discovery key on the swarm and sync it like any other core.

Multi-Writer Deployment

For high availability, run 3+ indexer instances:

┌───────────┐ ┌───────────┐ ┌───────────┐ │ Instance 1│ │ Instance 2│ │ Instance 3│ │ (indexer) │◄───►│ (indexer) │◄───►│ (indexer) │ │ │ │ │ │ │ │ writer │ │ writer │ │ writer │ │ core A │ │ core B │ │ core C │ └─────┬─────┘ └─────┬─────┘ └─────┬─────┘ │ │ │ └────────┬────────┴──────────────────┘ │ ▼ ┌────────────┐ │ Autobase │ Same view produced on │ View │ all 3 instances └────────────┘ • 1 instance down → service continues normally • 2 instances down → accepts writes, queues until return • 1 instance lost → rotate out, add replacement

Bootstrap: Adding Writers

  1. Start Instance 1 (first ever, no bootstrap key) — becomes sole indexer, outputs its base.key
  2. Start Instance 2 with --bootstrap <base.key> — joins, outputs its local.key
  3. On Instance 1: dispatch add-indexer operation with Instance 2's local key
  4. Instance 2 receives is-indexer event — now participates in consensus
  5. Repeat for Instance 3, 4, etc.
// In the apply handler, add-indexer dispatches:
await context.base.addWriter(key, { indexer: true })

// The new instance listens for confirmation:
base.on('is-indexer', () => {
  console.log('I am now an indexer!')
})

Use odd numbers of indexers (3, 5, 7) for clean majority quorum.

Hyperdispatch: Typed Operation Routing

Operations are schema-defined, encoded, and routed — not raw strings:

Appending an operation

const { encode } = schema.hyperdispatchSpec

// Encode a typed operation
const buf = encode(
  '@qvac-main-registry/put-model',
  modelData
)

// Append to local writer core
await this.base.append(buf)

Routing in apply()

const { Router } = schema.hyperdispatchSpec

const router = new Router()

router.add(
  '@qvac-main-registry/put-model',
  async (model, ctx) => {
    await ctx.view.putModel(model)
  }
)

// In apply:
for (const node of nodes) {
  await router.dispatch(
    node.value, { view, base }
  )
}

Hyperdispatch uses Hyperschema for binary encoding — compact, fast, and type-safe.

Key Properties of Autobase

Eventually Consistent

Writers append independently. The linearizer converges everyone to the same order. Different peers may temporarily see different states, but they'll converge.

Causal Ordering

If op B references op A, B will always come after A. Independent operations may be reordered freely.

Partition Tolerant

Writers can operate offline. When they reconnect, their operations merge into the DAG. CAP: picks AP over C.

Signed Checkpoints

Majority quorum locks ordering. Everything before the signed length is permanent — enables fast-forward for new peers.

Analogy: Git + Event Sourcing

Like Git

  • Multiple people commit independently
  • Commits reference parents (DAG)
  • Merging reconciles forks
  • History is append-only

Unlike Git

  • No manual merge conflicts — automatic linearization
  • No "branches" — one continuous view
  • No central server — fully P2P
  • Real-time — converges as operations arrive

Like Event Sourcing (Redux/Kafka)

  • Operations (events) are the source of truth, not the current state
  • State (view) is derived by replaying operations in order
  • The apply function is your reducer
  • Reordering = replaying events in a new order → same result

Common Pitfalls

Non-deterministic apply

// WRONG: external state
async apply(nodes, view) {
  for (const n of nodes) {
    await this.externalDb.update(n)
  }
}

// RIGHT: only view
async apply(nodes, view) {
  for (const n of nodes) {
    await view.put(n.value)
  }
}

Extension not disabled

// WRONG
new HyperDB(core, { extension: true })

// RIGHT (required for Autobase)
new HyperDB(core, { extension: false })

Assuming operation order

// WRONG: user may not exist yet
router.add('update-user', async (d) => {
  const user = await view.get(d.id)
  user.name = d.name // may be null!
})

// RIGHT: idempotent upsert
router.add('set-user', async (d) => {
  await view.put(d) // works either way
})

Not waiting for indexer status

// WRONG
await svc1.addWriter(svc2.local.key)
await svc2.putEntry(entry) // may fail!

// RIGHT
await svc1.addWriter(svc2.local.key)
await once(svc2.base, 'is-indexer')
await svc2.putEntry(entry)

Key Takeaways

  • Autobase = multi-writer layer on top of Hypercore
  • Uses event sourcing: writers append operations, linearizer orders them, apply function builds the view
  • Causal DAG ensures operations never precede their dependencies
  • Indexers build the view and advance the signed length via quorum
  • The apply function must be deterministic — same ops, same order → same view
  • In QVAC: Autobase sits between the writer instances and the HyperDB model catalog
  • Clients don't touch Autobase — they replicate the view core (read-only)
