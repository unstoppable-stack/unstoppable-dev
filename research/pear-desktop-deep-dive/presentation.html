Pear Desktop Deep Dive

The 10 things you need to know before building a Pear Desktop app

01 The Fundamental Model: Two Processes

RENDERER (Chromium / Electron) WORKER (Bare Runtime) ├── React, DOM, CSS ├── P2P: Hyperswarm, RPC ├── Browser APIs only ├── AI: @qvac/sdk ├── NO node:*, NO bare-* ├── Storage: Hyperbee, HyperDB └── pear-electron + pear-bridge └── bare-fs, bare-process, bare-crypto │ │ └──── NDJSON over pear-run pipe ──┘

This is not optional for apps using P2P, AI, or native modules. The renderer is a browser — it cannot import hyperswarm, @qvac/sdk, or even bare-fs.

02 When Do You Need a Worker?

FeatureNeeds Worker?Reason
React UI onlyNoBrowser context is enough
Hyperswarm (P2P)YesUses node:net under the hood
HyperDB / HyperbeeYesUses Hypercore (native)
QVAC SDK (AI inference)YesCompiled for Bare, not browser
File system accessYesbare-fs not available in browser
RPC over P2PYesbare-rpc is Bare-only
HTTP fetch to APIsNoBrowser fetch() works
localStorageNoBrowser API

Rule of thumb: any module starting with bare-* or hyper*, or @qvac/sdk, must run in a worker.

03 The Communication Pipe

Workers talk to the renderer through Pear.worker.pipe() — a bidirectional channel on file descriptor 3.

Renderer side (pear-run)

import run from "pear-run"

const pipe = run("/dist/worker/index.js", args)
pipe.write(JSON.stringify(msg) + "\n")
pipe.on("data", handler)

Worker side (Pear global)

const pipe = await Pear.worker.pipe()

pipe.write(JSON.stringify(msg) + "\n")
pipe.on("data", handler)

Critical gotcha: process.stdout goes to the terminal, NOT the renderer. The pipe is on fd 3. This was our most confusing bug — the worker looked like it was working but the UI received nothing.

04 The unrouted Config is Mandatory

"routes": "." makes ALL files web-routable. Without "unrouted", your worker JS file gets served as a web page in Chromium — showing raw source code instead of your UI.

{
  "pear": {
    "routes": ".",
    "unrouted": [
      "/dist/worker/index.js"
    ],
    "gui": {
      "width": 1224,
      "height": 808,
      "backgroundColor": "#151517"
    },
    "stage": {
      "entrypoints": ["/dist/worker/index.js", "/index.html", "/index.js"],
      "ignore": ["src", "worker", ".git"]
    }
  }
}

Every worker file must appear in both unrouted (exclude from routing) and stage.entrypoints (include in app bundle).

05 Bare Runtime is Minimal

Bare is not Node.js. It ships with almost nothing built-in.

Available in Bare

  • Uint8Array, ArrayBuffer, DataView
  • setTimeout, setInterval
  • console.log/error/warn
  • JSON, Math, Date, Promise
  • bare-process (npm install)
  • bare-fs (npm install)
  • bare-path (npm install)
  • bare-crypto (npm install)
  • bare-os (npm install)
  • bare-env (npm install)

NOT Available in Bare

  • TextEncoder / TextDecoder
  • URL / URLSearchParams
  • fetch / Request / Response
  • crypto (Web Crypto)
  • Buffer (use b4a package)
  • process (use bare-process)
  • fs (use bare-fs)
  • path (use bare-path)
  • btoa / atob
  • All node:* modules

Every bare-* module must be explicitly installed — forgetting one gives MODULE_NOT_FOUND.

06 Send workerReady BEFORE Slow Ops

Slow operations in Pear apps can take 30 seconds to several minutes:

  • DHT announce (discovery.flushed()) — 30+ seconds
  • Model download — minutes on first run
  • Autobase sync — variable

Wrong — UI times out

await initP2P()     // 30+ seconds
await loadModel()    // minutes
send({ type: "workerReady" })
// ← too late, UI already showed timeout

Right — UI starts immediately

send({ type: "workerReady" })
// UI unblocks ↑
await initP2P()     // background
await loadModel()    // background
send({ type: "modelStatus", status: "ready" })

07 The Entry Point Chain

package.json "pear" config │ ├── index.js ← Main process: pear-electron + pear-bridge │ └── loads index.html │ ├── index.html ← UI shell: <pear-ctrl> + <div id="root"> │ └── loads dist/src/live-reload.js │ └── imports ./index (React app) │ └── worker/index.ts ← Spawned by pear-run from renderer └── Pear.worker.pipe() for communication

Key dependencies per layer:

  • pear-electron + pear-bridge = renderer shell
  • pear-run = spawns worker from renderer
  • Pear.worker.pipe() = worker communication
  • Pear.teardown() = cleanup on exit

08 Build Tooling: SWC, Not Bundlers

Pear apps use SWC for file-to-file transpilation (TS → JS). No bundling — module resolution happens at runtime.

# Build both renderer and worker
bunx swc src -d dist --source-maps
bunx swc worker -d dist --source-maps

# Dev mode: concurrent watch + live reload
concurrently \
  "bunx swc src -d dist --source-maps --watch --config-file .swcrc.dev" \
  "bunx swc worker -d dist --source-maps --watch" \
  "pear run -d ."

.swcrc (production)

  • Minification with mangle
  • Dead code elimination
  • React Refresh off

.swcrc.dev (development)

  • No minification
  • Source maps enabled
  • React Refresh on

12 Quick-Start Checklist

  1. pear init --type desktop (or scaffold manually)
  2. Add pear-electron, pear-bridge, pear-run as dependencies
  3. Create index.js — main process bootstrap
  4. Create index.html — with <pear-ctrl> and #root
  5. Create src/ — renderer (React) code
  6. Create worker/ — Bare runtime code
  7. Configure package.json pear field: type, pre, routes, unrouted, gui, stage
  8. Install all bare-* modules needed by worker
  9. Set up SWC configs (.swcrc + .swcrc.dev)
  10. Build: bunx swc src -d dist && bunx swc worker -d dist
  11. Run: pear run -d .

Full research documents available in research/pear-desktop-deep-dive/ — 8 detailed docs covering architecture, worker pattern, Bare constraints, modules, build tooling, UI patterns, gotchas, and production patterns.
