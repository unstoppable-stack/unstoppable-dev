1. The Holepunch Data Stack

Everything is built in layers, starting from the append-only log.

APPLICATION LAYER HyperDB (schema + indexes) │ Hyperdrive (files + dirs) ───────────────────────────────┼─────────────────────────────── Autobase │ Hyperbee (multi-writer linearizer) │ (sorted B-tree on one core) ───────────────────────────────┴─────────────────────────────── Corestore (factory + key derivation + multi-core management) ─────────────────────────────────────────────────────────────── Hypercore (append-only log — the foundation) ─────────────────────────────────────────────────────────────── Hyperswarm (peer discovery + encrypted connections)
  • Hypercore: Append-only log, single writer, sparse replication, merkle-verified
  • Corestore: Manages many cores, deterministic key derivation, multiplexed replication
  • Hyperbee: Sorted KV on one core · Autobase: Merges multiple writers
  • HyperDB: Schema + indexes, P2P or local backend · Hyperdrive: P2P filesystem

2. Single-Writer vs Multi-Writer

Single Writer (Hypercore/Hyperbee)

  • One device holds the secret key and appends
  • Everyone else is a read-only replica
  • Zero conflict resolution — there's only one truth
  • Simple, fast, efficient

⚠ Writer must be online for new data

Multi-Writer (Autobase)

  • Multiple writers, each with their own Hypercore
  • Causal DAG linearized into deterministic order
  • Indexer quorum signs checkpoints (ordering locks)
  • Late joiners can fast-forward

✦ apply() MUST be deterministic — will be replayed on reorder

Rule: Use Autobase whenever multiple users OR multiple devices write to the same data.

⛔ Never store large blobs in Hyperbee. It bloats the B-tree. Store files in Hyperdrive, metadata in Hyperbee. Link them via paths.

4. How Keet Solves Multi-Device

Keet is fully P2P chat by Holepunch. Each room is an Autobase.

Multi-Device: Per-Device Writers

Phone (writer-phone) Desktop (writer-desktop) │ │ ▼ ▼ Autobase Room → Linearized View (same on both)
  • Each device gets its own writer Hypercore
  • Autobase merges all devices' writes
  • Device linking via QR code / secure key exchange

Identity: Key Pairs

  • 24-word seed phrase = master key
  • No email, no phone, no server
  • Corestore derives all keys from seed
  • Trade-off: lose seed → lose identity

File Sharing

  • Each file gets its own Hyperdrive
  • Drive key embedded in chat message
  • Sparse: only requested files download
  • No file size limit

6. When P2P Isn't Enough

Needs a Server

  • Global search — can't search data you don't have
  • User directory — finding users by name
  • Model registry — QVAC catalog of AI models
  • Financial transactions — global ordering
  • Push notifications — can't push to offline devices

P2P Handles Fine

  • Data storage — Hypercore/Hyperbee
  • File storage — Hyperdrive
  • Multi-writer — Autobase
  • Peer discovery — Hyperswarm DHT
  • AI inference — QVAC delegation
  • Identity — key-based auth

The Unstoppable Stack is ~90% P2P, with strategic centralization for discovery (model registry, search) and payments (WDK).

7. The QVAC Registry Pattern

The ideal hybrid: centralized discovery, P2P data transfer.

Client Registry Server Hyperdrive (P2P) │ │ │ │── list all models ────────►│ │ │◄── metadata (name, size, ─│ │ │ checksum, drive key) │ │ │ │ │ │── download model ─────────────────────────────────────────►│ │◄── model file (P2P) ──────────────────────────────────────│ │ │ │ │ Centralized: discovery │ P2P: data transfer │
  • qvacModelRegistryList() — queries centralized API for model metadata
  • qvacModelRegistrySearch({ filter: "whisper" }) — search by engine, name, type
  • Actual model download can be via Hyperdrive or HTTP

Pattern: The server helps you find things. Actual data is peer-to-peer.

8. Vault: Protocol-Level Replication

The Vault replicates Hypercores, not app data. It doesn't need to understand your data model.

Three Replication Modes

App DataVault Action
Hyperbee/Hypercorestore.get({ key }) + full download
AutobaseReplicate all writer cores via Corestore
HyperdriveReplicate + mirror to local FS

Design Principles

  • Read-only — never writes to app data
  • Corestore-per-app — isolation between apps
  • Full download — backup, not sparse cache
  • Just a peer — apps don't know it's a Vault

Compatible with any app because it works at the Corestore/replication level.

9. Vault Storage & Registration

Storage Layout

~/.unstoppable-vault/ ├── vault-store/ # Vault's own cores ├── apps/ │ ├── coffee-app/ # Corestore per app │ ├── notes-app/ # Isolated storage │ └── ... ├── drives/ │ ├── coffee-app/ │ │ └── files/ # Mirrored drive │ └── ... └── config/ ├── registry.json └── settings.json

Registration Protocol

// App → Vault
{
  type: 'register',
  appId: 'coffee-assistant',
  appName: 'Coffee Assistant',
  data: [{
    key: 'abc123...',
    kind: 'hyperbee',
    name: 'orders'
  }],
  drives: [{
    key: 'def456...',
    name: 'attachments',
    syncMode: 'full'
  }],
  requestAI: true
}

All apps join unstoppable:vault:discover:v1 topic. Vault acks with capabilities.

10. Multi-Vault & Cloud Transition

Laptop Vault Desktop Vault ┌──────────────────┐ ┌──────────────────┐ │ • Coffee App │◄────────────────►│ • Coffee App │ │ • Notes App │ Autobase │ • Finance App │ │ │ registry sync │ │ │ After sync: │ │ After sync: │ │ ALL apps ────────│──────────────────│───── ALL apps │ └──────────────────┘ └──────────────────┘

Vault-to-Vault Sync

  • Registry is an Autobase (both can write)
  • User-specific discovery topic from master key
  • Each Vault replicates cores/drives it doesn't have

Vault → Cloud (Same Protocol)

  • Cloud is a Vault hosted by Tether
  • Same replication protocol, same registration
  • Apps point to different topic + key, that's it
  • Adds: powerful GPUs, 24/7 uptime, subscription

Phase 1-2 is the MVP. It validates Corestore, Hyperdrive, and standalone Hypercore replication — three of the biggest agent pack gaps.

12. Quick Decision Tree

Do I need multi-writer? ├── Yes → Autobase + Hyperbee view └── No ├── Structured data → Hyperbee (simple) or HyperDB (schema) ├── Files → Hyperdrive └── Event stream → Raw Hypercore Do I need always-on availability? ├── Yes → Add Vault seeder (or Cloud) └── No → Pure P2P is fine Do I need global search / discovery? ├── Yes → Add centralized index (like QVAC registry) └── No → Hyperswarm DHT is enough Do I need multi-device write? ├── Yes → Per-device writer cores + Autobase (Keet pattern) └── No → Single Hypercore is fine

The Vault is compatible with all these patterns because it operates at the replication layer, not the data model layer.

Key Takeaway

The Unstoppable Vault is just another peer with good uptime.
It replicates at the Corestore level, so it's compatible with any app.
The Cloud is the same thing, hosted remotely. Apps don't need to change.
