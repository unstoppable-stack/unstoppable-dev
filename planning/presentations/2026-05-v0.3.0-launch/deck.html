Build profiles — minimal vs full

The mechanism

  • tsup.config.ts defines two profiles selected via US_BUILD_PROFILE
  • Each command gated by a build-time flag: US_FEAT_INIT/SCAFFOLD/DOCTOR/REMOTE/RESEARCH/SEARCH
  • esbuild's define pass replaces them with literal true/false
  • Dynamic import() behind the gate → bundler DCEs the entire module tree when off
  • us --version prints the active profile, e.g. 0.3.0 (minimal)

What ships on npm

{
  "scripts": {
    "build:minimal": "US_BUILD_PROFILE=minimal tsup",
    "build:full":    "US_BUILD_PROFILE=full tsup",
    "prepack":       "US_BUILD_PROFILE=minimal tsup",
    "test:full":     "pnpm build:full && vitest run"
  }
}

npm publish automatically runs the minimal build via prepack. Remote daemon code stays in the repo for development but doesn't bloat the published tarball.

expo-mobile — AI section & chat UI

What scaffolded apps now have

  • Visible GPU/CPU device toggle (ai-device-switch)
  • Load Assistant button + status pill
  • Chat input + role-scoped chat-bubble-{role} testIDs
  • Empty messages filtered — assistant bubble only mounts when content arrives
  • Optional node-sync wiring — app boots, dials the local Node, registers its Hyperbee, surfaces sync status

Why testIDs matter

The role-scoped IDs are what make Maestro flows deterministic. Before: a generic chat-bubble matched the user's own message and the assertion passed before inference even started. Now: chat-bubble-assistant only exists when the model actually replied.

testID stability role-scoped node-sync ready

E2E inference verification — three modes

ModeHow to invokeWhat it verifiesTime
Sim + mock QVAC_MOCK=1 ... :local-ai UI wiring, Load → chat input → Mock: reply ~45s
Sim + real :local-ai (no mock) AI section renders, GPU/CPU toggle, no BareKit / TurboModuleRegistry red-box ~45s
--device <udid> pnpm test:e2e -- --device IPHONE_UDID Real model load (5 min), real prompt, real chat-bubble-assistant, no native errors ~6–7 min

Why three modes: Maestro 2.3.0 + Expo dev client tap delivery on the Load Assistant button is unreliable on the iOS simulator — manual taps work, automated ones don't propagate to onPress. Real inference verification therefore lives in --device mode; the simulator catches the regressions it can catch reliably (native module linkage, UI wiring). Full reasoning documented inline in src/e2e/maestro-flow.ts.

Streaming inference

New wire messages: inference, inference-token, inference-done, inference-error. NodeClient.requestInference() is an async iterator.

requireServices: ['ai']

Bare-runtime portable now: node-client and the daemon's protocol.js lazy-load os and guard process.pid/uptime(). The full NodeDaemon runs inside Bare/Pear workers without patches — that's what makes node-desktop possible.

packages/node-desktop/ — Pear dashboard

What it shows

  • Service pills — data / files / ai (lit by nodeHello)
  • Summary cards — paired apps, cores, drives, peers
  • Paired-app list with per-row Unpair button
  • Live event log via pear-bridge

How to run

pear run .                  # plain node, no AI
pear run . --ai-mock        # echo AI for UI work
pear run . --ai             # real QVAC model

Why this matters

The dashboard is the node — same NodeDaemon embedded in the Pear worker. No "GUI talks to daemon" plumbing, no second process to babysit. Apps paired via us continue to work when the dashboard is the node.

pear-electron 1.7 pear-bridge 1.2 unstoppable-node

Generators wired

node-sync feature flag is now opt-in across node-cli, pear-desktop and expo-mobile. Apps fall back gracefully if the local node isn't running.
