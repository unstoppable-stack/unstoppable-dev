1. What the Demo Showed

A small model (1–3B parameters) was fine-tuned with LoRA and became extremely good at specific tool calls — matching or exceeding much larger models at that narrow task.

Before Fine-Tuning

Small model guesses tool call format. JSON errors, wrong argument names, hallucinated tools. You need a 7B+ model for reliability.

After LoRA

Same small model nails the exact tool format every time. Correct arguments, proper JSON, right tool selection. On a 1–3B model.

Why It Works

Fine-tuning doesn't teach "general intelligence." It teaches the model the exact output pattern for your specific tools.

2. Fine-Tuning & LoRA Concepts

What is Fine-Tuning?

A pre-trained model has learned language from trillions of tokens. Fine-tuning adjusts its behavior for a specific task by training on a curated dataset of examples.

Think of it like: the model already knows how to speak — fine-tuning teaches it how to speak in your context.

Three Levels of Customization

LevelWhat It DoesTraining Required?
PromptingTell the model what to do in contextNone
RAGGive the model knowledge at query timeNone (embeddings only)
Fine-TuningChange the model's weights permanentlyYes — hours on 1 GPU

When to Fine-Tune (and When Not To)

Use CaseFine-Tune?
Consistent output format (JSON, schemas)Yes
Reliable tool calling on small modelsYes
Domain jargon / styleYes
Replace a 7B model with a 1B model for specific tasksYes
General Q&ANo — use prompting
Access to external knowledgeNo — use RAG
Less than 500 examples availableNo — not enough data

What is LoRA?

Low-Rank Adaptation. Instead of updating all 7 billion parameters, LoRA adds tiny adapter matrices (0.1–5% of the model size) to specific layers. Only these adapters are trained. The base model stays frozen.

Base Model (7B params, frozen 🔒)  +  LoRA Adapter (4–33M params, trained ✏️)  =  Specialized Model

The adapter is a small file (~50–200 MB). You can have many adapters for one base model — swap them depending on the task. Like installing plugins.

LoRA Adapter Sizes

Rank (r)Trainable ParamsVRAM NeededAdapter File Size
r = 8~4M~16 GB~16 MB
r = 16~8M~18 GB~32 MB
r = 32~16M~20 GB~64 MB
r = 64~33M~24 GB~130 MB

QLoRA — Even Less VRAM

QLoRA quantizes the base model to 4-bit before training. Cuts memory by 75%. A 7B model trains on a single consumer GPU (16 GB). A 3B model trains on ~6 GB.

4. The Dataset

Quality of data is the single biggest factor in fine-tuning success.

Format: JSONL with Chat Messages

Same format QVAC already uses. One JSON object per line.

Basic conversation

{"messages": [
  {"role": "system", "content": "You are a helpful assistant."},
  {"role": "user", "content": "What's the weather in Tokyo?"},
  {"role": "assistant", "content": "It's 22°C and sunny in Tokyo."}
]}

With tool calls (this is the important one)

{"messages": [
  {"role": "user", "content": "Weather in Tokyo?"},
  {"role": "assistant", "tool_calls": [
    {"id": "call_1", "type": "function",
     "function": {"name": "get_weather", "arguments": "{\"city\":\"Tokyo\"}"}}
  ]},
  {"role": "tool", "content": "22°C, sunny"},
  {"role": "assistant", "content": "Tokyo is 22°C and sunny right now."}
],
"tools": [
  {"type": "function", "function": {
    "name": "get_weather",
    "description": "Get current weather for a city",
    "parameters": {"type": "object",
      "properties": {"city": {"type": "string"}},
      "required": ["city"]}
  }}
]}

Each model's chat template converts this to the right token format at training time. Qwen uses <tool_call> XML tags, Llama uses <|python_tag|>, Mistral uses [TOOL_CALLS]. You don't worry about encoding — the training pipeline handles it.

How Much Data Do You Need?

SizeQualityVerdict
< 500 examplesModel memorizes instead of generalizingAvoid
500 – 1,000Works for narrow tasks (single tool, simple patterns)Minimum
1,000 – 5,000Good generalization, handles edge cases, robust outputSweet spot
5,000 – 10,000Excellent for multi-tool, diverse tasks, complex reasoningIdeal
> 10,000Diminishing returns — better to improve qualityOverkill

100 perfect examples > 10,000 sloppy ones.

For tool calling specifically: each tool needs 50–100 diverse examples minimum. 10 tools = 500–1,000 just for tool selection. Add edge cases (ambiguous queries, multi-tool calls, error handling, "no tool needed") and you're at 2,000–3,000.

Always split: 90% training / 10% evaluation (to detect overfitting).

What Makes a Good vs Bad Dataset

Good Dataset

  • Consistent formatting across all examples
  • Diverse inputs — different phrasings, edge cases
  • Accurate outputs — each example is a correct answer
  • Covers failure modes — "no matching tool" examples
  • Real-world distribution — reflects actual usage
  • Multi-turn when needed — tool result → response

Bad Dataset

  • Copy-paste templates with minor word changes
  • Contradictory examples — same input, different outputs
  • Missing edge cases — only "happy path"
  • Inconsistent formats — sometimes JSON, sometimes text
  • Wrong outputs — tool calls with incorrect arguments
  • Too narrow — all examples use the same 3 words

Good Diversity Example

// Same tool, different phrasings:
"What's the weather in Tokyo?"
"Tokyo weather please"
"How hot is it in Tokyo right now?"
"Is it raining in Tokyo?"
"Temperature in Tokyo, Japan"
"Give me Tokyo forecast"

// Edge cases:
"Weather in"              → error: missing city
"Weather in Abc123"       → error: invalid city
"Tell me a joke"          → no tool needed (just respond)
"Weather and horoscope"   → multi-tool call

Common Mistakes

MistakeWhat Happens
Only happy-path examplesModel crashes on unexpected input
All examples start with "Please"Model only responds to polite requests
Single-tool onlyModel can't choose between tools
No "no tool needed" examplesModel forces a tool call on everything
Training on generated data without human reviewAmplifies errors and weird patterns

5. Gathering Training Data

Four strategies — from recording real usage to synthetic generation.

Strategy 1: Record Real Conversations

The gold standard — learn from actual usage.

1. User interacts with the agent normally
2. Log every conversation as JSONL (messages + tools)
3. Filter: keep only successful interactions
4. Human review for quality + correctness
5. Clean, deduplicate, split → training dataset
Keep ✓Discard ✗
Task completed successfullyAgent got stuck in a loop
User confirmed result was correctUser had to correct the agent
Tool calls returned valid resultsTool calls failed or errored
Concise exchange (2–6 turns)Very long wandering conversation

Best for: Apps already in use with real users. Highest quality if users rate interactions.

Strategy 2: Synthetic Data Generation

Use a large model to create training data for a small one.

1. Define your tools (Zod schemas, descriptions)
2. Write 10–20 seed examples by hand
3. Ask a strong model (70B / Claude / GPT-4) to generate variations
4. Verify: format check + semantic check + execute tool calls
5. Human spot-check 10–20% of generated data

Prompting the generator

Given these tool definitions:
{tools}

And these seed examples:
{seed_examples}

Generate 50 diverse user queries that would require using these tools.

Requirements:
- Vary phrasing (formal, casual, terse)
- Include edge cases
- Include multi-tool scenarios
- Include "no tool needed" cases
- Include ambiguous queries
- Each query must be unique

Verification pipeline

Seed examples (20)  →  Generate (5000)
                          ↓
                    Format check: valid JSON? correct schema?
                          ↓
                    Semantic check: does the tool call match the query?
                          ↓
                    Execution check: do the arguments pass Zod validation?
                          ↓
                    Clean dataset (3000-4000 after filtering)

Available tools: SynthCall ToolWeave Azure Synthesizer DIY with Claude/GPT

Strategy 3: Trajectory Distillation

The "teacher-student" pattern — a big model teaches a small one.

1. Teacher (70B / cloud) runs your tasks with your tools
2. Record every message exchange as JSONL trajectory
3. Filter: keep successful trajectories, discard failures
4. Student (1–3B local) fine-tuned on these trajectories

The small model doesn't need to figure out the reasoning — it just needs to learn the pattern of correct tool usage. The big model already did the hard thinking. 

// Run 500 coding tasks with GPT-4 / Claude
// using your exact tool definitions:
const tools = [
  { name: "read_file", ... },
  { name: "write_file", ... },
  { name: "search_files", ... },
  { name: "run_terminal", ... }
];

// For each task, save the full trajectory:
// user → assistant(tool_call) → tool(result) → assistant(tool_call) → ...

// Filter to 300-400 clean trajectories
// Fine-tune Qwen 3 1B on these
// Result: 1B model that uses YOUR tools reliably

Cost efficiency: Pay for cloud inference once to generate training data. Then run the fine-tuned small model locally forever. No recurring API costs.

Strategy 4: P2P Trajectory Collection

The Unstoppable Stack advantage — community-powered datasets.

1. User A's agent solves a task → trajectory saved locally
2. User A rates outcome ⭐⭐⭐⭐⭐ → opts in to share
3. Trajectory (anonymized) → HyperDB via Hyperswarm
4. Users B, C, D also contribute trajectories
5. Aggregated dataset → anyone can train a better adapter
6. Adapter shared as GGUF (~100 MB) via Hyperdrive

No Central Server

Data never touches a company server. Users control what they share. Fully opt-in, anonymized.

Network Effect

More users = more trajectories = better adapters = better agent = more users.

Adapter Distribution

Trained adapters are tiny GGUF files. Perfect for P2P via Hyperdrive. No model registry needed.

6. Technical Pipeline

Training Steps

1. Prepare — Curate JSONL dataset, 90/10 split
2. Configure — Choose rank, alpha, target modules, learning rate
3. Train — SFT with PEFT/TRL or Unsloth (2–8 hours, 1 GPU)
4. Evaluate — Check eval loss, run test prompts
5. Convert — Export to GGUF format for llama.cpp
6. Deploy — Load alongside base model in QVAC

Recommended Hyperparameters

ParameterValueNotes
LoRA rank (r)16–32Higher = more capacity, more VRAM
LoRA alpha32–64Usually 2× rank
Target modulesq_proj, k_proj, v_proj, o_projAttention layers
Learning rate2e-4With cosine schedule
Batch size4+ gradient accumulation 4
Epochs3Watch eval loss — stop if it rises
Warmup ratio0.110% of total steps
LR schedulercosine

LoRA in llama.cpp (what QVAC uses)

llama.cpp already has full LoRA support:

  • GGUF adapter format — convert any HuggingFace PEFT LoRA to GGUF
  • Hot-swap at runtime — change adapters without reloading the model
  • Multiple adapters simultaneously — load several, control each scale independently
  • Scaled application — dial adapter influence from 0.0 to 1.0
  • KV cache aware — cache keys include active adapter state

Server API

GET  /lora-adapters       → list loaded adapters + current scales
POST /lora-adapters       → update adapter scales

# Load model with multiple adapters pre-loaded:
llama-server --model base.gguf \
  --lora tool-calling.gguf \
  --lora code-style.gguf \
  --lora-init-without-apply    # load but don't activate yet

How QVAC could expose this

import { loadModel, completion } from "@qvac/sdk";

const modelId = await loadModel({
  modelSrc: QWEN_3_1B_Q4,
  modelType: "llm",
  modelConfig: {
    lora: [
      { src: "tool-calling-adapter.gguf", scale: 1.0 },
      { src: "code-style-adapter.gguf", scale: 0.5 }
    ]
  }
});

// The 1B model now reliably calls tools
const result = completion({ modelId, history, tools, stream: true });

Key numbers: Base model ~700 MB (1B Q4) + adapter ~50 MB = ~750 MB total for a tool-calling specialist that runs on a phone.

7. Unstoppable Stack Use Cases

Use Case 1: Tool Calling Specialist

Make a tiny model reliable at YOUR app's specific tools.

Problem: Tool calling on small models (1–3B) is unreliable. JSON errors, wrong tool selection, hallucinated arguments. Today you need Qwen 3.1 7B for reliable tools.

Solution: Fine-tune a 1–3B model on your app's exact Zod schemas. The model learns the specific output format, tool names, and argument structures.

MetricBefore (1B base)After LoRA
Tool call accuracy~40%~95%
JSON parse errors~30%<2%
Model size700 MB750 MB (+adapter)
Speed (tok/s)~150~145 (minimal loss)
RAM needed2 GB2.1 GB

Impact for QVAC apps: Tool calling on mobile devices. A 1B model with a LoRA adapter runs on a phone at 150 tok/s while reliably calling your app's tools. No 7B model needed.

Use Case 2: Unstoppable Stack Coding Agent

An agent that "knows" Pear, Hyperswarm, HyperDB, QVAC natively.

Problem: General models don't know our stack. They put P2P modules in the renderer (crash), forget TextEncoder polyfills in Bare, use wrong API versions. Today we solve this with agent-pack rules and skills (prompt-level).

Fine-tuning approach: Collect coding trajectories from building real apps. Fine-tune a local model on these. The model internalizes the patterns instead of needing them in the prompt every time.

Dataset sources we already have

PatternSource
Worker pattern for Pear Desktopcoffee-assistant-ui
Pear.worker.pipe() wiringfixes/ folders
Hyperswarm topic creationrecipes
HyperDB multi-writer setupskills
QVAC streaming + tool callsbattle-tested apps
bare-* explicit installsfixes/ folders

The dream: A 3B local model that writes correct Pear Desktop apps on first try — because it learned from hundreds of real builds. No prompt engineering needed. The knowledge is in the weights.

Use Case 3: P2P Adapter Sharing

Distribute specialized models across the network.

LoRA adapters are tiny (50–200 MB), hot-swappable, and in GGUF format. Perfect for P2P distribution via Hyperdrive.

1. Developer trains a LoRA adapter
2. Exports as GGUF (~100 MB)
3. Published to Hyperdrive
4. Peers discover via Hyperswarm
5. Hot-swap into QVAC runtime — no model reload

Think of it like npm for model specializations. Someone trains a "Pear Desktop" adapter. Someone else trains "QVAC RAG." Browse adapters, check ratings, hot-swap into your runtime. Fully decentralized.

8. The Fine-Tuning Flywheel

→ Users build apps with QVAC + tools
→ Agent trajectories saved locally
→ Trajectories shared P2P (opt-in)
→ LoRA adapters trained on aggregated data
→ Better adapters shared via Hyperdrive
→ Users get better agents → build more → repeat

Each iteration: more users → more data → better adapters → better agents → more users. P2P distribution makes this compound across the network.

9. Key Takeaways

LoRA Makes Small Models Specialists

A 1–3B model with a LoRA adapter can match a 7B model at specific tasks. Huge for on-device, mobile, and resource-constrained deployments.

Dataset Quality is Everything

1,000–5,000 high-quality examples > 50,000 sloppy ones. Consistent formats, diverse inputs, real edge cases. No shortcuts.

Multiple Paths to Gather Data

Record real usage, generate synthetically, distill from big models, or collect P2P. Start with synthetic + distillation, graduate to real trajectories.

P2P Adapter Sharing is Our Edge

LoRA adapters are tiny (50–200 MB). Hot-swappable. Distributable via Hyperdrive. No other stack can do decentralized model specialization.

Bottom line: QVAC + LoRA = specialized AI that runs on any device, gets better from community usage, and distributes peer-to-peer. That's truly unstoppable AI.
